# 006: Azure agent orchestration and inspectable outcomes

Date: 22 September 2026. Scope: PH-06, requested next by the user. Azure calls are authorized; desktop remains the browser target.

The user requested Phase 6 while Phase 5 was still open. This phase includes the prerequisite desktop start/stop, run activity, response preview, outbox, package and note views. It does not mark the full manual response editor/development-control workflow complete. The Phase 4 API had already verified the complete simulator path before introducing the agent.

The server uses the existing configured Azure deployment and OpenAI v1 Chat Completions protocol. Each request requires one strict function call; parallel model tool calls are disabled. There is no scenario script in the runtime agent. The model inspects current facts and saved results, chooses a tool, receives its actual result and refreshed observation, and continues or requests a verified pending/completed outcome. Deterministic test models are injectable only in Python tests and carry `source=test_double`. The application has no replay/model-substitution switch.

The model selects response type, concern dispositions, claims with evidence IDs and attachment IDs. The server binds case/simulation/client/loan scope, action IDs, observed versions, authorized recipient, sender and mandatory disclosures. Claims and attachments still pass the Phase 3 validator, and the response uses its controlled rendering. Arbitrary model prose cannot become a borrower response. Dates, amounts, document identity, tax status and concern coverage are checked by the existing rule boundary. A model statement cannot establish delivery or closure.

Model writes use the existing simulator dispatcher. It checks the worker's live lease and stop flag inside the same SQLite write reservation as the mutation; receipts and simulator events retain the run ID. A model cannot supply failure modes, another client, recipient overrides, approvals, a shell command or an external connector. Selecting automatic mode cannot override a client review requirement. Selecting review-required mode adds a send approval requirement even for an otherwise automatic client.

The local worker owns one persisted execution slot. It checkpoints before model requests, before tools, after results and at completion. A run stores provider/configuration fingerprint, prompt/tool versions, limits, usage, action/evidence references, result codes and pending work. Keys, endpoint/deployment values, provider free text and hidden reasoning are not saved to these run records. Source Office documents and acceptance-oracle files are never loaded into the model context. Only current scoped synthetic evidence and curated guidance are used. Successful retrievals are retained together; replacing earlier retrieval results caused a repeated-read loop in the initial live experiment and was corrected before acceptance.

Default limits are 28 steps, 28 model calls, 300 seconds, 250,000 reported tokens (raised from 150,000 on September 24, 2026, because the two-round name-change run used up to 140k), 1,600 completion tokens per request and 100,000 context characters. Each is configurable in `.env.example`; omitted fields use defaults without modifying the user's `.env`. Total tokens are checked after provider usage is reported, so the last in-flight request can exceed that threshold; no resulting action is executed after a usage/time limit is reached. Request timeouts, call/output/context caps and a run deadline independently bound execution. Three errors with the same code, or three identical reads without a changed case/input basis, pause the run. Provider failures are reported with controlled codes, without an automatic retry.

Stop requests halt before the next action. An action already executing may commit; its receipt remains visible. Uncertain/in-progress results immediately pause and block subsequent writes. Restarted expired runs pause for inspection rather than blindly replaying an action. Automatic reconstruction/resumption after process failure remains Phase 8. Phase 7 still owns reviewer decisions, edited approvals, specialist flows and interactive evidence resumption.

The desktop polls persisted reads only; browser refresh or case switching cannot issue a start/send mutation. Selected case identity survives refresh. Each run shows whether it used live Azure or a test double, its activity and pending reason. Response/outbox/package/note viewers read actual persisted simulator records; package downloads recheck scope and hashes. The API retains event cursors; a streaming transport is not required for this local implementation.

Validation includes deterministic worker/contract regressions plus real Azure evaluations of DEMO-02 with and without its document and with an embedded instruction attempting recipient substitution and false closure. See [Phase 6 checkpoint evidence](../checkpoints/PH-06.md). Results remain distinct from the unfinished five-family acceptance and recovery phases.
