# 004: Scoped simulators, durable action results and Azure verification

Date: 22 September 2026. Scope: PH-04. The user requested desktop support only for now and reiterated authorization for live Azure testing when needed.

Four local modules implement the planned CCT, ILS, OnBase and secure-mail operations. Their common dispatcher accepts typed commands scoped by simulation, case, loan and client. The registry also exposes existing knowledge/rules and read-only review/status inspection. No company servicing, mail or document connector is present. The separate live Azure probe tests the model provider; it is not a servicing operation or an enabled agent tool.

CCT reads cases, worklists, related cases and history; records the supported classification/routing/concern/pending plan; and closes only after the completion gate passes. ILS reads loan/task/history records, reuses matching tasks, creates a distinct authorized ordinary-name-update task, executes that permitted update and records a final note. Unsupported task creation remains rejected: missing tax/bankruptcy tasks do not themselves authorize creation. A task belonging to another related case is reused with its original case reference. No arbitrary status/result injection or funds movement is exposed.

Secure mail prepares a validated structured candidate and records a local outbox entry with the actual body, sender, recipient, evidence versions and immutable copies of the sent attachments. OnBase indexes a manifest and a readable combined PDF containing the case correspondence, actual response and sent attachments. Retrieval verifies content hashes and case scope. Reusing an existing send/package/note under a new action ID still returns the existing resource rather than creating a duplicate.

The index uses **Sherman ID = the exact loan identifier**, preserving leading zeros, and the case's **CCID**. `Borrower Correspondence (Demo)` is an explicit synthetic Document Type mapping (`synthetic-index-v1`); the source did not establish an approved production type for every response branch. `INQ Email Reply` is the Correspondence Type for the configured email demo. Final notes use **Department = Servicing**, **INQ Email Reply**, **Standout Comment**, the actual recipient and delivery/tracking reference. This supersedes PH-03's provisional `ILS/final` labels. PH-03's JSON-only archive contract is extended to require the combined PDF and its manifest/hash.

Each write carries a stable action ID, current case revision, complete evidence-version snapshot and decision-input fingerprint. The dispatcher reserves the SQLite writer and commits receipts, side effects and audit events together. Identical retries return the prior receipt; changed payloads under the same ID return a conflict. Known failures require a fresh action ID and current preflight. Pending review does not become approval merely because an action is retried. Review issuance remains PH-07; current valid persisted approvals are enforced now, and review-required sends remain paused otherwise.

The explicit presenter failure controls are `before_write` and `after_write_response_lost`. They are excluded from business action identity and model tool parameter schemas. A lost response leaves the applied local records intact and the receipt uncertain. Further writes are blocked until `action.reconcile` independently verifies the original resource and any retained files. Reconciliation never repeats the original write. Rejected reconciliation retains uncertainty. Files created by a failed savepoint are removed without touching earlier artifacts. Process-crash cleanup of unreferenced files and broader worker recovery remain PH-08.

Case `revision` protects mutations; `content_revision` identifies the latest material state on which a response is based. Classification, concern planning, owner edits and servicing/task updates change the content basis. Send/closure lifecycle updates advance the case revision without altering that content basis. Decision fingerprints exclude case/related-case status, revision and update timestamp, while retaining content revision, owners, classifications, routing, pending plans, concerns, evidence, task facts, policy and client settings. Consequently a send cannot invalidate its own reviewed response, while a material change still does. Existing PH-03 assessment histories remain immutable; old draft validations must be revalidated against the current schema. Migration `0004` initializes content revision from the existing revision and adds servicing history and final-note details.

`scripts/demo-simulators.ps1` creates a fresh DEMO-02 and calls the same API/dispatcher for plan, preparation, send, index, note and closure. Its output is explicitly a deterministic development demonstration. It does not start an AI run. The full browser response editor, outbox/package views and execution controls remain PH-05. Existing UI screens show the persisted case outcome, simulator history and validation results.

The live Azure probe uses the deployment configured in the user's `.env`, without substituting a model. It makes at most two requests: require a scoped read function call, execute it against a fresh isolated synthetic case, then verify the model's JSON answer against the returned facts. The explicit `--live`/PowerShell helper is the opt-in; regular app startup and test suites make no model calls. It records a configuration fingerprint, timestamp, pass/fail checks and token usage without saving keys, endpoint, deployment value or raw provider responses. Setup status reports the last successful check only for matching current configuration. This verifies connectivity and tool-call protocol, not full agent behavior or every future tool schema.

Protocol reference fetched during implementation: [official OpenAI function-calling documentation](https://developers.openai.com/api/docs/guides/function-calling). Azure uses the preconfigured `/openai/v1/` endpoint and deployed model name.

Desktop Edge is the current browser verification target. The mobile Playwright project was removed from the default checks as requested; existing responsive CSS is retained. PH-05 and later phases remain separate work.
