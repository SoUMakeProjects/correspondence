# 003: Deterministic business assessment and validation

Date: 22 September 2026. Scope: PH-03; Azure calls are authorized by the user but are unnecessary for these deterministic checks.

Routing, evidence prerequisites, authority, response checks and completion checks are Python domain services. They read persisted synthetic inputs and actual document files. They do not invoke a model, change case status, update servicing facts, create tasks, send correspondence or approve a draft.

The business policy is [phase3.v1.json](../../data/policies/phase3.v1.json), version `demo-rules-1.0`. The receipt clock uses `America/New_York`, weekday calendar `eastern-mon-fri-v1`, receipt day zero, evaluation day inclusive and no holiday exclusions. Routing retains the inquiry/dispute assessment independently of the operational taxonomy and the communication channel/queue. Conflicting special routes retain all restrictions and require supervisory disposition. Assignment dates never enter the age calculation.

The selected version-1 fixtures supply reviewed scenario intake facts; additional cases require their own supported procedure. Runtime code never loads the evaluation-only expected outcomes. Only document-request row S03:r122 and neutral tax-payment row S03:r103 have exact applicable taxonomy mappings in this release. Name-change requests, ambiguous EFT requests and credit/bankruptcy concerns retain an explicit mapping exception; the nearby failure/allegation labels are not automatically applicable to neutral requests. Credit reporting retains GAP-08 even after the supplied specialist determination.

Requester roles and recipients are checked separately. The synthetic servicing snapshot supplies borrower identity; other roles need matching authorization evidence. Representative-only communication requires verified representative evidence; representation alone does not create C&D. Active C&D remains blocking until an approved reversal workflow processes written evidence. No reversal execution is added in PH-03. Client snapshots, product applicability and conflicting ILS/CSP recipients are checked before a response.

Assessments propose dispositions for every known concern. Additional concerns require their own researched disposition. Pending plans retain a reason, owner, resume requirement and next review. The next review defaults to the next Eastern weekday at the same local time; this is a documented demo scheduling convention, not a production SLA. Tax questions may be answered from the recorded schedule while disbursement remains pending. Task matching includes loan/client and action-specific request facts. A relevant task is reused, and its completed flag alone cannot prove the underlying action occurred.

`GET /assessment` computes a fresh preview. `POST /assessments` records immutable inputs, policy, file checks, report and fingerprint in `rule_evaluations`, plus a case event. The request ID prevents duplicate records, and an expected revision plus SQLite writer reservation makes capture atomic with case edits. Retries return the original recorded report. Assessment history is distinct from the current preview; recording does not increment case revision or execute the recommendation. Migration `0003` adds these records and a nullable review content hash while preserving prior application data.

Response preflight accepts a typed candidate containing all concern dispositions, structured factual claims, evidence versions, attachments, client/sender/recipient and disclosure selections. A claim must agree with both its cited evidence and the authoritative case facts. Completion claims also require the supported task result. Attachments are checked for actual bytes, hash, readability, identity and relevance. The body is a controlled rendering of these checked inputs. Supplying other prose returns `unchecked_response_text`; PH-03 does not claim to verify arbitrary natural-language statements. The response editor and AI drafting adapter belong to PH-05 through PH-07. Repetitive responses and production dispute-result wording require later applicable procedures and are not inferred from these fixtures.

Completion is a read-only gate over persisted records. The latest draft must still match its structured candidate, case/evidence versions and input fingerprint. Required review must bind to the candidate and input hash, in addition to draft/version/revision; old approvals with no hash are insufficient. All concerns must have supported persisted resolution, and the exact response needs a successful simulated send, a verified archived package and a final ILS note. Interim requests and referrals do not close a case. After delivery, incomplete records produce `records_incomplete`.

The Phase 4 integration contract uses operations `csp.send`, `onbase.index` and `ils.final_note` with successful `simulated_complete` receipts. The outbox snapshot binds draft ID/version, case revision, body, recipient and attachment IDs. The indexed file is a JSON archive of that exact snapshot, checked by content hash; index fields bind the case, loan, draft, outbox and body hash. Source attachments remain scoped, versioned files and are revalidated by the gate. A later printable PDF can accompany this manifest. No simulator writes or delivery are exposed by Phase 3. No selected fixture supplies an approved no-response exception, so the gate cannot invent one.

The UI exposes current routing, clock basis, authority, concern plans, prerequisites, completion checks and recording of assessment evidence. The existing owner/status controls remain limited to queue/review changes. Phase 4 remains the next implementation phase.
